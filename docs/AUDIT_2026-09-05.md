## Scope and evidence boundary

This audit reconstructs the Movia 1–4 technical chronology from the project artifacts available in the current workspace: Git history, ADRs, baseline manifests, source trees, acceptance scripts, live Termux services, Android package state, and the Movia native agent. The tool context did not expose arbitrary historical ChatGPT transcript bodies, so this document does not claim a byte-for-byte extraction of every old chat message.

## Chronological playback architecture

### 1. Initial Media3 player

Early commits introduced a Compose player backed by AndroidX Media3/ExoPlayer, followed by persistence, Picture-in-Picture, subtitles/scaling, shared mini-player, MediaSession integration, rotation handling, gestures, and track controls. No current project evidence supports VLC, libVLC, or mpv as the active Movia playback engine.

### 2. 0.7.x — transition from demonstration/fallback media to real stream resolution

The 0.7.x line progressively removed demo/fallback video and synthetic links, added real stream resolution, multiple voice/quality candidates, on-demand resolver logic, balancer/provider aggregation, and P2P resilience. Synthetic Big Buck Bunny/test links and synthetic 404-style sources were explicitly purged.

### 3. 0.9.11 / ADR-281 — timeline and settings corrections

The player added a fallback duration path for P2P/containers where Media3 duration was unavailable and connected voice/quality selectors to `switchToStream` while preserving playback position.

### 4. 0.9.12 / ADR-282 — domain playback architecture

Playback was refactored around `PlaybackRequest`, `StreamCandidate`, `StreamDeduplicator`, `StreamRanker`, and `DomainPlaybackResolver`. Resolution became a domain concern rather than a UI list of URLs. Failure memory, ranking, fallback ordering, and explicit `NO_SOURCE` state were introduced.

### 5. 0.9.28 / ADR-284 — correct voice/stream semantics

A key UI/player mismatch was fixed: `PlayerScreen` had been reading static catalog streams instead of the reactive `PlaybackSession.streamOptions`. Voice selection was changed to select a complete `StreamOption` and preserve provider metadata/headers. Studio/voice labels were separated from internal Media3 audio-track identity.

### 6. 0.9.29 / ADR-285 — clean-room direct provider and timeout resilience

The closed Zona-compatible source path was observed returning HTTP 500 and causing long waits. The project added a clean-room Collaps provider, prioritized usable direct HLS candidates, shortened failure paths for hard HTTP failures, stopped waiting synchronously for cancelled provider pools, and increased relevant transport timeouts. Public torrent providers remained environmentally variable.

### 7. 0.9.29 / ADR-286 — stale magnet-only cards and refresh behavior

Catalog entries containing only stale magnet candidates could leave Media3 buffering without obtaining a direct playable source. The resolver was changed to refresh direct provider candidates when no direct URL was available. Background enrichers were de-emphasized to reduce CPU load.

### 8. 0.9.30 / ADR-287 — root Media3 HLS/DASH module defect

The decisive engine-level failure was identified: `media3-exoplayer` alone did not provide the HLS/DASH media-source implementations required by current streams. Explicit dependencies were added:

- `androidx.media3:media3-exoplayer-hls:1.9.3`
- `androidx.media3:media3-exoplayer-dash:1.9.3`

The player is also constructed on the main looper. This removed the `HlsMediaSource` class-loading failure that prevented otherwise valid HLS streams from starting.

### 9. 0.9.32 — current audited state

The current `PlaybackSession` uses candidate-aware request profiles, provider headers supplied by candidate metadata rather than hostname guessing, retry/failure classification, reload-before-fallback behavior, stable stream identity, in-place Media3 track switching when candidates share the same locator, explicit HLS/DASH support, and a local gateway for P2P candidates.

During this audit, basic playback was proven on the installed application. A separate agent bug was then found: `player.selectVoice` waited for `isPlaying` plus position movement even when the user had paused playback. The switch itself succeeded but the operation remained `RUNNING`. The operation policy was changed so a paused session may complete a stream/track selection when the requested variant is active and playback state is `READY`; the stricter movement gate remains for actively playing sessions. The patched APK was rebuilt, installed, and the paused voice-switch operation completed successfully.

## Garbage / repository split-brain found

### Android working tree

The development checkout had accumulated tracked `.bak-*` files and historical diagnostic/log material. Generated content included roughly 226 MiB of `app/build`, Gradle/Kotlin caches, several ~24 MiB APK copies, and diagnostic outputs. The small working-tree `.gitignore` was insufficient for the full project.

### Backend working tree

The backend tree was approximately 9.7 GiB during the audit, dominated by runtime data rather than source:

- `torrent_cache`: ~5.0 GiB
- `backups`: ~3.0 GiB
- `.tmp_native_probe`: ~803 MiB
- `catalog.db`: ~758 MiB
- `stream_cache`: ~130 MiB
- logs: ~34 MiB

`catalog.db` is runtime state and must not be deleted merely to make Git smaller. Cache/temp directories are regenerable; backups require retention review before deletion.

### Canonical Git repository

`/storage/emulated/0/Movia` was based on an older 0.9.23 baseline while the installed and working source had advanced to 0.9.32. The canonical branch also contained one local commit not yet pushed. Source synchronization repaired this split-brain while preserving runtime databases, caches, secrets, APKs, and recovery snapshots outside Git.

## Repository policy

Git stores source code, tests, ADRs, reproducible configuration, and baseline metadata. It does not store Android build outputs, APKs, catalog databases, stream/torrent caches, backend backups, runtime state, logs, diagnostics, MCP scratch projects, `.trashed-*`/`.bak-*` recovery files, or secrets.

Change discipline:

1. One logical change per commit.
2. Run relevant tests/build gates.
3. Run `git diff --check`.
4. Run a secret scan on changed source paths.
5. Commit with a scoped Conventional Commit message (`fix:`, `feat:`, `refactor:`, `test:`, `docs:`, `chore:`).
6. Push immediately after a green commit so the phone is not the only copy.

## Post-push cleanup and revalidation

The canonical `main` branch was pushed successfully and the local/remote HEAD hashes matched at `e183f264ceea7047218b15ef0ad600e772ebd82c` before local runtime cleanup began.

Cleanup was deliberately limited to reproducible or redundant local data:

- the backend's own `cache_pruner.py` removed 8,120,114,688 bytes by its accounting while preserving one protected torrent-cache entry;
- Android `app/build` was removed;
- backend `.tmp_native_probe` was removed;
- backend `stream_cache` was emptied and its directory retained;
- four legacy schema-2 catalog DB snapshots were reduced to the newest snapshot (`catalog.pre-zona-cache-20260831-135800.db`), compressed to a verified gzip archive of about 151 MiB; the three older redundant snapshots were removed;
- the live schema-4 `catalog.db` was not deleted or modified by the cleanup procedure;
- managed `torrent_cache` was not forcibly deleted after pruning because it is dynamic runtime state and the pruner had an active protected entry.

After cleanup, `movia-media-parser` remained running and `127.0.0.1:8888/health` still returned HTTP 200. A fresh native-agent playback request for `Сплит` again completed with Media3 `READY`, `isPlaying=true`, active `1080p / Дубляж`, and advancing position. Playback was then paused normally. This confirms that the deleted build/cache/temp artifacts were not required for the verified direct-HLS runtime path.
